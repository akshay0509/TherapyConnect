API Reference

Every REST endpoint, grouped by service. Paths shown are the external gateway paths the SPA calls; the gateway strips the leading prefix before forwarding. Expand any endpoint for request/response detail and side effects.

Conventions

Public paths: /auth/**, /user/create-user, /user/forgot-username, /user/forgot-password, /user/reset-password, the Razorpay /webhook/**, and the Google Forms intake webhook /integrations/google-forms/*/submissions (both signature-verified rather than JWT-authenticated). /admin/** requires ADMIN authority; everything else needs a valid Authorization: Bearer <jwt>. Service-internal routes (/*/internal/**) are denied at the gateway and only reachable service-to-service. The therapistId / userId are read from JWT claims server-side via SecurityUtils — clients never send them in the body (a field marked “from JWT” is populated by the server). The gateway routes by prefix: /therapist/* → therapist-service, /appointment/* → appointment-service, /client/* → client-service, /user/* → user-service, /analytics/* → analytics-service.

Authentication gateway · /auth

POST/auth/loginAuthenticate & issue tokens

Auth: public · rate-limited to 10 attempts / 60s per client IP (custom LoginRateLimiter, HTTP 429 when exceeded).

Request

AuthRequest{ "username": "jdoe", "password": "••••••••" }

Responses

  • 200 — { "token": "<jwt>" } plus Set-Cookie: refresh_token (httpOnly, Secure, SameSite=None, path /auth/refresh, 7-day).
  • 401 — { "failureReason": "INVALID_CREDENTIALS | ACCOUNT_LOCKED | ACCOUNT_DISABLED | SERVICE_UNAVAILABLE" }
  • 429 — { "error": "Too many login attempts…" }
  • 503 — { "message": "Cannot sign in right now — the therapist service is unavailable…" }. Only for THERAPIST logins when the profile lookup can't be reached: issuing a token that asserts "no profile" would route an existing therapist into creating a duplicate one, so login fails retryably instead.

Flow & side effects: validates via UserServiceProxy.validateUser (circuit-broken); publishes auth-login-success/auth-login-failure to Kafka; resolves therapistId from TherapistService; signs a 15-min RS256 JWT; persists a REFRESH_TOKENS row (deleting any prior tokens for the user).

POST/auth/admin-loginAdmin console login

Auth: public · rate-limited to 5 attempts / 60s per client IP (LoginRateLimiter, stricter than user login since there is no account lockout).

Request: { "username": "…", "password": "…" } — checked against the ADMIN_USERNAME/ADMIN_PASSWORD env credentials with a constant-time comparison.

Responses: 200 { "token": "<jwt>" } — an 8-hour JWT with authorities:["ADMIN"] and userId:"admin" (no refresh token) · 401 invalid · 429 rate-limited.

POST/auth/refreshRotate refresh token, issue new access token

Auth: refresh_token cookie · Request: none (cookie only).

Responses: 200 { "token": "<jwt>" } + new rotated cookie · 401 { "error": "No refresh token" | "Invalid or expired refresh token" }.

Side effects: deletes the presented token and issues a fresh one (rotation). Now preserves the user's roles (persisted on the refresh-token row) and back-fills therapistId if it was null at login — so refreshed tokens carry full authorities. The cookie is SameSite=None; Secure for the cross-site SPA.

POST/auth/logoutRevoke refresh token

Auth: refresh cookie (optional) · Response: 200 always, with a cleared cookie (maxAge=0).

Side effects: deletes the user’s refresh tokens (revocation) if the cookie is present.

POST/auth/forgot-passwordRequest a reset email

Auth: public · Request: { "email": "user@example.com" }

Response: 200 { "message": "If the email exists, reset instructions will be sent." } — generic by design (no account enumeration). Proxies to UserService.

POST/auth/reset-passwordComplete a password reset

Auth: public (token-scoped) · Request: { "token": "…", "newPassword": "…" }

Response: 200 { "message": "Password reset successfully." }. Token must be unused and within its 30-minute window. Proxies to UserService.

Auth: public · Request: { "token": "…", "newPassword": "…" } · Response: 200. Rejects invalid/expired tokens (IllegalArgumentException → handled by GlobalExceptionHandler). Clears the token on success.

GET/user/accountCurrent account details

Auth: JWT (username from token) · Response

AccountDetailsDto{ "username", "email", "userRole", "createdAt",
  "lastLoginTime", "lastLoginIp", "lastLoginUserAgent" }

Backs the Account Settings page and pre-fills the therapist-setup email.

PUT/user/change-passwordLogged-in password change

Auth: JWT · Request: { "currentPassword": "…", "newPassword": "…" }

Response: 200 { message }. Verifies the current password, applies the same policy as reset, and rejects a new password identical to the current one (400 on any failure).

PUT/user/update-accountUpdate email/username

Auth: JWT (username resolved from token, not body) · Request

UpdateAccountRequest{ "username": "newname", "email": "new@x.com", "currentPassword": "••••" }

Response: 200 updated UserDto. Requires the correct currentPassword; blank fields are ignored. Values are trimmed and validated — username must match [A-Za-z0-9._-]{3,30}, email must be well-formed, and both are checked for uniqueness (friendly 400 instead of a DB-constraint 500).

Services & delivery modes

POST/therapist/create-service-with-modeCreate a service + its first delivery mode

Auth: JWT · Request: ServiceWithModeRequest — { "service": {…TherapistServicesDto}, "mode": {…TherapyDeliveryModeDto} } · Response: the created TherapistServicesDto.

Appointment appointment-service · /appointment

POST/appointment/create-appointmentBook a slot

Auth: JWT (therapistId from token) · Request

BookAppointmentRequest{ "slotId": "SLT…", "clientId": "CLT…", "modeId": "…",
  "clientName": "Jane", "customPrice": 1500.00 }   // customPrice optional — overrides the mode's default fee

Response: 200 BookAppointmentResponse — { appointmentId, paymentStatus, paymentLinkUrl, clientNotified }. The payment fields are populated only when the therapist has payments enabled (otherwise null). Errors: SlotNotAvailableException (unknown/blocked slot or invalid mode), SlotAlreadyBookedException (lost the race).

Flow: slotId identifies the starting 30-minute block. The active delivery mode supplies the serviceId and price (must be positive — a zero/null fee would corrupt earnings and produce an invalid Razorpay amount); the service's duration comes from TherapistServiceProjection and determines the appointment end, rounded up to a 30-minute boundary. The request is rejected if an unavailable override covers the window or it overlaps an existing active appointment. The appointment row is inserted and flushed (to get its id), then GenericBlockReservationService.reserve locks the whole run of blocks and stamps each with the appointmentId — any block already taken raises SlotAlreadyBookedException and the entire transaction rolls back. Finally AppointmentCreated goes to the outbox, and a Razorpay link is created best-effort (never fails the booking — worst case paymentStatus=LINK_FAILED, retry via /payments/{id}/link). Validation failures return 400 VALIDATION_ERROR. See the reservation model.

PATCH/appointment/update-appointmentStatus transition

Auth: JWT · Request

UpdateAppointmentStatusRequest{ "appointmentId": "…", "status": "CONFIRMED", "reason": null }

Allowed targets: CONFIRMED | COMPLETED | CANCELLED | ABANDONED. Terminal states are immutable. CANCELLED releases the slot. Emits the matching event (AppointmentConfirmed, …). Payments: CANCELLED/ABANDONED best-effort cancel any unpaid payment link (COMPLETED is excluded so a post-session payment can still be collected). Errors: InvalidAppointmentStatusTransitionException, AppointmentNotFoundException.

PATCH/appointment/reschedule-appointmentMove to a new slot

Auth: JWT · Request

RescheduleAppointmentRequest{ "appointmentId": "…", "newSlotId": "SLT…", "modeId": "…"?, "reason": "…"? }

Response: 200 "Appointment rescheduled". Uses GenericBlockReservationService.move — the union of the old and new block intervals is locked once so a partially overlapping reschedule can retain blocks it already owns instead of releasing and re-acquiring them. Re-prices by mode, re-derives the end time from the service duration, sets status RESCHEDULED, emits AppointmentRescheduled (with old/new slot + times). Rejects reschedules of terminal appointments or to the same slot. Payments: since the fee may change, any unpaid link is cancelled and a fresh one issued at the new fee (a PAID payment is left untouched).

Payments appointment-service · /payments & /webhook

Razorpay Payment Links. Active only when the therapist has payments enabled and Razorpay keys are configured (otherwise a silent no-op — the platform's global kill switch). See the payment workflow and the Razorpay Setup Guide.

GET/payments/{appointmentId}Payment status for an appointment

Auth: JWT (scoped to therapistId) · Response: PaymentInfoDto — { appointmentId, status, amount, currency, paymentLinkUrl, razorpayPaymentId, clientNotified, failureReason, updatedAt }, or 404 if none. status ∈ {LINK_CREATED, LINK_FAILED, PAID, EXPIRED, CANCELLED}.

POST/payments/{appointmentId}/linkCreate / retry the payment link

Auth: JWT · Response: 200 PaymentInfoDto, or 422 when payments don't apply (disabled, terminal appointment, or no positive fee). Idempotent: reuses an existing LINK_CREATED/PAID link; re-issues after a LINK_FAILED/EXPIRED/CANCELLED. This is the recovery path when link creation failed during booking.

POST/webhook/razorpayRazorpay webhook (public)

Auth: none — authenticity is the X-Razorpay-Signature HMAC-SHA256 over the raw body (constant-time compared against RAZORPAY_WEBHOOK_SECRET). Invalid/missing signature → 401.

Events handled: payment_link.paid (mark PAID → auto-confirm the appointment + emit AppointmentConfirmed), payment_link.cancelled, payment_link.expired, payment.failed (records the reason; link stays active for retry). Always returns 200 after the signature check — processing is idempotent, so retries can't help and shouldn't be triggered.

Public URL: registered in the Razorpay dashboard as {host}:8091/appointment/webhook/razorpay (the gateway strips /appointment).

POST/admin/outbox/replayReplay outbox events (appointment-service)

Request: { "from": "YYYY-MM-DDTHH:MM:SS" } (defaults to midnight today; 400 on bad format). Re-publishes outbox events from that time — an operational recovery tool if a consumer missed messages. This is also the un-park path: parked poison events in the range get parked=false, retryCount=0 and re-enter rotation (see poison-event parking).

GET/admin/kafkaKafka / DLQ overview (gateway)

Response: { dlts: [{ topic, originalTopic, pending, total, lastMessageAt }], groups: [{ groupId, state, totalLag, topics }], totalPending }. "Pending" = DLT messages not yet replayed, measured against the dlt-replay group's committed offsets. Consumer-group lag is computed against main topics only. 500 { error } if Kafka is unreachable.

GET/admin/kafka/dlt/{topic}/messagesPeek pending DLT messages

Query: ?limit (default 20, max 50) · Response: oldest-first list of { partition, offset, timestamp, key, payload (truncated at 4000 chars), exceptionMessage, originalTopic } — the exception message comes from the kafka_dlt-* headers. 400 if the topic doesn't end in .DLT.

POST/admin/kafka/dlt/{topic}/replayReplay a DLT back to its source topic

Republishes all pending messages to their original topic (from the kafka_dlt-original-topic header, falling back to the topic name minus .DLT), with synchronous sends, then commits the dlt-replay group's offsets so they stop counting as pending. Response: { topic, replayed }. Safe to repeat — consumers are idempotent.

Client intake (Google Forms)

Prospective clients submit a Google Form; submissions are staged for therapist review before becoming clients. See the intake workflow.

POST/integrations/google-forms/{integrationId}/submissionsGoogle Forms webhook (public)

Auth: no JWT — authenticity is an HMAC-SHA256 over <timestamp>.<raw body> keyed by GOOGLE_FORMS_HMAC_SECRET, sent hex-encoded. Required headers: X-Integration-Timestamp (epoch seconds) and X-Integration-Signature.

Request: GoogleFormSubmission — { responseId, submittedAt, answers: { fullName, firstName, lastName, dob, pronouns, gender, qualification, occupation, phoneNumber, email, preferredDays, preferredTimings, preferredModes, emergencyContact*, consent } }.

Lenient parsing: respondents' locales vary, so a date may arrive as 29/03/1983 rather than ISO. Ambiguity is resolved deliberately, not guessed — if either component exceeds 12 the order is certain; only when both could be a month does it fall back to day-first (en-IN convention). Rejecting these previously returned 400, Apps Script marked the row FAILED, and the prospective client was never seen. First/last name are also derived from fullName at staging (not approval), so the therapist can correct an odd split in the review form; anything the form actually collected wins.

Responses: 202 Accepted with the staged ClientIntakeDto · 401 unknown integration, bad/absent signature, or timestamp outside the skew window (default 300s) · 400 missing responseId, unparseable date/number, or consent not accepted.

Idempotent on (integrationId, responseId) — a redelivered submission returns the existing intake. Fails closed when the integration is unconfigured.

POST/client/intakes/{intakeId}/approveApprove → create client

Auth: JWT · Request: { "client": { …IntakeClientData } } — optional; omit to accept the submission as-is, or supply corrected values (the intake row is updated to match what was approved).

Response: IntakeDecisionResponse { intakeId, status, clientId }. Creates the Client with source=GOOGLE_FORM and emits ClientCreated. The approval payload may also set the client's negotiated sessionFee and dsf flag — a negative fee is rejected and zero collapses to null; for a DSF client the fee is left null, since pro-bono is decided at booking time rather than stored twice. Requires full name + DOB and consent still accepted; only PENDING intakes are reviewable, and re-approving is a no-op that returns the existing decision.

POST/client/intakes/{intakeId}/rejectReject an intake

Auth: JWT · Request: { "reason": "…" } (optional) · Response: IntakeDecisionResponse. Records the reason and reviewer; no client is created.

Error handling

UserService, ClientService, TherapistService and AppointmentService each register a GlobalExceptionHandler (@RestControllerAdvice) mapping domain exceptions to a consistent ApiError body. Appointment-specific exceptions: SlotNotAvailableException, SlotAlreadyBookedException, AppointmentNotFoundException, InvalidAppointmentStatusTransitionException, AvailabilityProjectionConflictException.
