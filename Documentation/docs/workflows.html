Business Workflows

End-to-end traces of the core processes, showing the synchronous calls, events, projections and side effects involved in each.

1 · Login & token issuance

Validates credentials, records the attempt asynchronously, and mints a scoped JWT.

sequenceDiagram autonumber participant B as Browser participant GW as Gateway participant US as User participant TS as Therapist participant K as Kafka B->>GW: POST /auth/login GW->>US: POST /validate-user (circuit-broken) US-->>GW: AuthResponse(authenticated, roles, userId) alt not authenticated GW->>K: publish auth-login-failure GW-->>B: 401 { failureReason } else authenticated GW->>K: publish auth-login-success GW->>TS: GET /internal/therapist/user/{userId} TS-->>GW: therapistId GW->>GW: sign JWT (15m) + create refresh token GW-->>B: 200 { token } + refresh cookie end K-->>US: login event consumed → audit + lockout/reset

Async aftermath: the User service's consumers write USER_LOGIN_AUDIT, update last-login fields on success (resetting failedAttempts), and on failure increment the counter — locking the account at 5.

Therapist lookup: unknown ≠ absent

The therapistId lookup is only performed for users whose roles include THERAPIST, so a client isn't held hostage by a TherapistService restart. More importantly, the lookup now distinguishes "this user has no profile" (a 200 with an empty body) from "we couldn't ask" (TherapistLookupUnavailableException from the circuit-breaker fallback). Previously both produced null, so a therapist logging in during a restart received a token asserting they had no profile — the SPA then routed them to create one, and createTherapist had no duplicate guard, writing a second profile for the same user. Login now fails with a retryable 503 instead: a momentary outage is a far smaller problem than a split identity.

2 · Availability → generic 30-minute blocks

⚡ Architecture change: slot generation is decoupled from services

Availability used to be generated per service — one slot per (service × time), each carrying a serviceId and fee. That created parallel overlapping slots at the same time and made double-booking prevention awkward. Availability is now a single stream of generic 30-minute blocks that know nothing about services. A booking reserves however many consecutive blocks the chosen service needs. Fewer rows, no duplicate times, and one obvious concurrency boundary.

The therapist defines weekly rules and date overrides, then generates blocks. Generation is the bridge between TherapistService (owner) and AppointmentService (booking engine).

sequenceDiagram autonumber participant T as Therapist (UI) participant TS as TherapistService participant DB as TS DB participant K as Kafka participant AS as AppointmentService T->>TS: POST /generate-slots?start&end TS->>TS: reject if active appointments overlap TS->>DB: delete existing blocks in range TS->>DB: chop rules into uniform 30-min blocks
(de-duplicated by therapist+start+end) TS->>DB: apply "available" overrides TS->>DB: save blocks + outbox(AvailabilitySlotsGenerated) Note over TS,DB: one transaction K-->>AS: AvailabilitySlotsGenerated AS->>AS: refuse if BOOKED blocks in range
else replace AVAILABLE projection rows

Block math: each rule's time window is chopped into uniform 30-minute blocks, independent of any service. Blocks are de-duplicated on therapistId + startTime + endTime (a DB unique constraint backs this in the AppointmentService projection), so overlapping rules can't produce duplicates. Blocks carry no serviceId and no fee — both are resolved at booking time from the chosen delivery mode. Overrides remain single-day windows.

3 · Booking an appointment

The most important transaction in the system. AppointmentService derives the session length from its local service projection, then reserves a contiguous run of availability blocks under row locks.

sequenceDiagram autonumber participant T as Therapist (UI) participant AS as AppointmentService participant DB as AS DB participant K as Kafka participant TS as Therapist participant AN as Analytics T->>AS: POST /create-appointment {slotId, modeId, client} AS->>DB: find starting block (else SlotNotAvailable) AS->>DB: find active delivery mode → serviceId + price AS->>DB: resolve fee: DSF → custom → client rate → mode price AS->>DB: resolve service duration (TherapistServiceProjection) AS->>AS: end = start + duration (rounded up to a 30-min boundary) AS->>DB: reject if an unavailable override covers the window AS->>DB: reject if window overlaps an active appointment AS->>DB: insert appointment (flush → appointmentId) AS->>DB: reserve(): SELECT … FOR UPDATE the block run,
validate exact sequence, stamp appointmentId alt any block taken AS-->>T: SlotAlreadyBooked (whole tx rolls back) else reserved AS->>DB: outbox(AppointmentCreated) AS-->>T: 200 BookAppointmentResponse K-->>TS: AppointmentCreated → AppointmentProjection(SCHEDULED) K-->>AN: (ignored until Completed) end

Fee resolution & the stamped-fee invariant

The fee is resolved once, at booking, and stamped onto the appointment. Precedence, highest first:

#SourceEffect
0Client is DSF (pro bono)Always 0. Nothing overrides it.
1customPrice typed at bookingOne-off override for this appointment.
2Client's negotiated sessionFeeA standing flat rate for that client.
3Delivery mode priceThe standard rate.
Invariant: sessionFee == 0 ⟺ the session was pro bono

This holds structurally — the DSF branch is the only one that can return zero, and every other branch is validated positive before returning. Resolution and validation are the same step, so there's no second pass that could re-derive a different answer.

Why stamping matters: because the resolved amount is frozen on the appointment, later changes to a client's rate or DSF flag never rewrite historical bookings. Earnings sums the stamped fee instead of joining the client's current flag. Previously the DSF flag was read at display time, so a client who paid normally and later moved to DSF had every past session's earning silently rewritten to zero while the fee column still showed what they actually paid — the two columns contradicted each other and totals under-reported real income.

Block reservation (GenericBlockReservationService)

All multi-block state changes go through one service that owns the concurrency boundary. It locks the overlapping rows in stable chronological order (lockOverlappingBlocks), validates, then mutates — so a transaction either takes the whole interval or nothing.

OperationBehavior
reserveEvery block in the run must be AVAILABLE with no owner; each is set BOOKED + stamped with the appointmentId. Any taken block ⇒ SlotAlreadyBookedException.
releaseRequires every block to be owned by this appointment (ownership mismatch is an IllegalStateException — a data-integrity bug, not a user error), then returns them to AVAILABLE.
moveReschedule without a release-then-reserve gap: locks the union of old and new intervals once, in one order, so partially overlapping moves can retain blocks this appointment already owns while claiming the new-only ones. Avoids both deadlocks and a window where someone else grabs the retained blocks.

Alignment: a session needn't fill whole blocks — a 50-minute appointment occupies a 60-minute footprint on the 30-minute grid, which preserves the changeover gap and keeps the next start on the clock. Rounding lives in blockAlignedEnd so reserve, release and move can never disagree about which blocks an appointment owns. Validation rejects intervals that aren't a positive multiple of 30 minutes, or where the locked rows don't form an exact gap-free sequence.

Overlap guard: booking and rescheduling also check existsActiveAppointmentOverlap — any SCHEDULED/CONFIRMED/RESCHEDULED appointment overlapping the requested window is rejected with SlotNotAvailableException, independent of block state.

4 · Appointment state machine

Status transitions enforced by AppointmentService. Manual targets are limited to CONFIRMED/COMPLETED/CANCELLED/ABANDONED; terminal states cannot change.

stateDiagram-v2 [*] --> SCHEDULED: AppointmentCreated SCHEDULED --> CONFIRMED: confirm SCHEDULED --> RESCHEDULED: reschedule CONFIRMED --> RESCHEDULED: reschedule RESCHEDULED --> CONFIRMED: confirm CONFIRMED --> COMPLETED: complete SCHEDULED --> CANCELLED: cancel (releases blocks) CONFIRMED --> CANCELLED: cancel (releases blocks) SCHEDULED --> ABANDONED: abandon (no-show, still billable) CONFIRMED --> ABANDONED: abandon (no-show, still billable) COMPLETED --> [*] CANCELLED --> [*] ABANDONED --> [*]
  • CANCELLED releases the reserved blocks via GenericBlockReservationService.release.
  • RESCHEDULED uses move (union-locked, no release-then-reserve gap), re-prices by mode, and emits AppointmentRescheduled with old/new times.
  • ABANDONED is a no-show: the blocks are released, but the session is still billable — it counts toward earnings at the full fee (see rollups).
  • Terminal states (COMPLETED/CANCELLED/ABANDONED) reject further transitions and reschedules.

5 · Calendar sync (Notification)

Notification reacts to appointment events to manage Google Calendar invites — including a Google Meet link for online sessions.

EventAction in Google Calendar
AppointmentConfirmedCreate event with therapist+client attendees; Meet conference if ONLINE, location if OFFLINE; store mapping (idempotent — skips if a mapping already exists). Blank attendee emails are skipped rather than sent (a blank email fails the whole insert).
AppointmentRescheduledUpdate the existing event's times/mode (skips if no prior invite). Switching OFFLINE→ONLINE now adds a Meet link; updates set conferenceDataVersion=1, without which the Calendar API silently ignores conference changes.
AppointmentCancelledDelete the event (sendUpdates=all) and remove the mapping.
CalendarBlockCreated/DeletedCreate/delete a "blocked time" calendar event when syncToGoogleCalendar is true.

Attendee identity is per-therapist: invites use the email from Notification's THERAPIST_PROJECTION (kept current by TherapistCreated/TherapistUpdated/TherapistPaymentSettingsUpdated events — changing your email in Account Settings propagates here), falling back to the THERAPIST_EMAIL env value only for rows that predate the email field. The client-side ClientProjection likewise upserts on ClientUpdated, so client contact edits reach future invites. Calendar failures are no longer swallowed — they retry (5s × 2) and dead-letter to <topic>.DLT for admin inspection and replay.

6 · Payment collection (Razorpay)

When the therapist has payments enabled and Razorpay keys are configured, booking creates a payment link and a successful payment auto-confirms the appointment. Payment can never block or fail a booking — every Razorpay call is wrapped and failures are recorded on the payment row.

sequenceDiagram autonumber participant T as Therapist (UI) participant AS as AppointmentService participant RZ as Razorpay participant CL as Client participant K as Kafka participant NS as Notification T->>AS: POST /create-appointment AS->>AS: book (status SCHEDULED) — commits first AS->>RZ: create payment link (amount, notes.appointmentId) RZ-->>CL: SMS / email with link AS-->>T: BookAppointmentResponse { paymentLinkUrl, paymentStatus } CL->>RZ: pays the link RZ->>AS: POST /webhook/razorpay (X-Razorpay-Signature) AS->>AS: verify HMAC → mark PAID (idempotent) AS->>AS: auto-confirm (SCHEDULED/RESCHEDULED → CONFIRMED) AS->>K: AppointmentConfirmed (outbox) K-->>NS: create Google Calendar invite
TriggerPayment action
BookingCreate link (reuse if one already LINK_CREATED/PAID). Response carries paymentStatus, paymentLinkUrl, clientNotified.
Link failed at bookingpaymentStatus=LINK_FAILED; therapist retries via POST /payments/{id}/link.
payment_link.paid webhookMark PAID, auto-confirm the appointment, emit AppointmentConfirmed. If the appointment was already terminal, log for manual refund.

Kill switch & enablement: if Razorpay keys are blank or the therapist's paymentEnabled projection (from TherapistEvent) is off, every payment method is a silent no-op and bookings behave exactly as before. See the Razorpay Setup Guide.

7 · Admin operations

The admin console authenticates separately (POST /auth/admin-login → 8-hour ADMIN token) and drives ADMIN-gated endpoints across services: a live service-health grid (Gateway /admin/services via Eureka + actuator), a Kafka/DLQ monitor (Gateway /admin/kafka — DLT depth, consumer-group lag, message peek, and one-click replay back to the source topic), user management (list, enable/lock, force-reset password, login audit), rollup-freshness health (Analytics), and an outbox replay tool (Appointment /admin/outbox/replay) to re-publish events from a given time if a consumer missed them.

The recovery model is now two-sided: the outbox replay covers events that never reached Kafka's consumers, while the DLT replay covers events that reached a consumer but failed processing (e.g. an expired Google token). Both are safe to repeat because consumers are idempotent.

8 · Analytics rollups

Analytics consumes appointment events and maintains daily aggregates + retention projections. Only certain event types affect counters:

EventEffect
AppointmentCompleted+completed; earnings += the stamped sessionFee (already 0 for a pro-bono session, so no second DSF test); paid/dsf & online/offline counters; per-service rollup; bump client engagement (lastSession, totalSessions).
AppointmentCancelled+cancelled on the session's day.
AppointmentAbandoned+abandoned.
AppointmentRescheduled+rescheduled (counted against the original date).

Retention queries derive retained (>1 session), churned (no session in 30 days), retention rate, average sessions/client, and a session-frequency histogram (1, 2-3, 4-6, 7-10, 10+).

Billing model: a no-show still bills

The therapist's earnings view (TherapistService, computed from AppointmentProjection) treats billable as COMPLETED + ABANDONED — a client who doesn't show is charged the full fee. Abandoned counts are also broken out separately (week/month/lifetimeAbandonedCount) so the therapist can see what share of income came from sessions nobody attended. DSF (sliding-fee) sessions remain zero-money but are counted as delivered work, tracked in their own counters.

9 · Clinical risk tracking

The therapist records a risk assessment per client, and the system reminds them when it's due for review. TherapistService owns this; the encrypted fields use the same AES-GCM converter as session notes.

Deliberately never derived

The risk level is recorded by the therapist, never computed by the app — not from attendance, cancellations, or note content. The stated rationale is that an algorithmic risk score is a clinical assessment made by software that has never met the client, and a therapist who either trusts it or is contradicted by it is worse off than with nothing. The app holds the assessment and reminds about it; the therapist makes it.

LevelReview intervalNotes
NONE—An assessed judgement of "no risk". No review ever falls due.
LOW90 days
MODERATE60 days
HIGH15 days15 rather than 14 so the prompt lands the day before a fortnightly session, leaving time to prepare rather than arriving as the client does.

The interval lives on the level itself, so the cadence follows the judgement automatically — raising someone to HIGH brings their next review forward without reconfiguring anything. A per-client reviewIntervalDaysOverride can supersede it.

  • Never assessed vs. assessed NONE — the DTO exposes neverAssessed separately, because "nobody has looked at this yet" is materially different from "a clinician judged there is no risk".
  • Derived server-side — effectiveIntervalDays, reviewDueAt and reviewDue are computed by TherapistService so the review rule lives in one place; the UI renders them rather than recomputing.
  • Audit trail — every save appends a CLIENT_RISK_REVIEW row capturing previous level → new level, reviewer and timestamp.
  • Encrypted at rest — the free-text concern and safetyPlan use the same field-level AES-GCM encryption as session notes.

10 · Client intake via Google Forms

Prospective clients fill in a public Google Form; an Apps Script posts each submission to ClientService, where it is staged for review rather than becoming a client directly. The therapist then approves (optionally editing the data first) or rejects it.

12 · Password reset & forgot username

Gateway → User. Forgot password: User issues a 30-minute token and emails a reset link via the Gmail API; reset consumes the token. Forgot username: User looks up the account by email and emails the username. Both always return a generic response to avoid account enumeration, and email-send failures are logged (not surfaced to the caller).
